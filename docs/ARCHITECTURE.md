# Архитектура

## Обзор

Модульный монолит: один процесс ASP.NET Core обслуживает HTTP API и статические файлы Blazor WebAssembly
(клиент и API имеют один origin). Данные — в PostgreSQL. Миграции схемы выполняются отдельной задачей
(EF Core migration bundle) от имени владельца схемы; приложение работает от роли только с DML-правами.

```
 Браузер (Blazor WASM, access-токен только в памяти)
    │  HTTPS, Authorization: Bearer <JWT 5 мин>; refresh — cookie __Host-pp_refresh (HttpOnly, Secure, SameSite=Strict)
    ▼
 nginx (TLS 1.2/1.3, лимиты на IP, перезапись X-Forwarded-*)          ← граница доверия: интернет
    │  HTTP во внутренней сети
    ▼
 PersonalPlatform.Api (ASP.NET Core)                                    ← граница доверия: доверенный прокси
   middleware: ForwardedHeaders (только известный прокси) → CorrelationId → лимит тела → журнал запросов →
               заголовки безопасности → обработчик исключений → маршрутизация → аутентификация JWT +
               проверка сеанса → авторизация (deny-by-default) → rate limiting → таймауты → контроллеры
    │  Npgsql, роль pp_app (SELECT/INSERT/UPDATE/DELETE), statement_timeout 30 с
    ▼
 PostgreSQL 17 (схема app; составные FK (id, owner_id); CHECK-ограничения; xmin для конкуренции)
```

## Проекты и зависимости

| Проект | Ответственность | Может зависеть от |
|---|---|---|
| `Domain` | сущности, инварианты, расчёты (повторения, серии привычек, бюджеты, проводки) | только BCL |
| `Contracts` | DTO запросов/ответов, перечисления, лимиты API | только BCL |
| `Application` | сценарии использования (сервисы), валидаторы FluentValidation, порты (`IAppDbContext`, `ICurrentUser`, `ITextSearch`, `IUserDirectory`) | Domain, Contracts, EF Core (абстракции запросов) |
| `Infrastructure` | `AppDbContext`, конфигурации EF, миграции, Identity, JWT и сеансы, email, фоновые службы | Application, Domain |
| `Api` | контроллеры, middleware, политика безопасности, хостинг клиента | все серверные проекты |
| `Client` | UI | только Contracts |

Правила проверяются тестами `tests/PersonalPlatform.ArchitectureTests` по скомпилированным сборкам
(ссылки между сборками, отсутствие `DbContext` в контроллерах, отсутствие публичных сеттеров у сущностей и т.д.).

## Ключевые решения

1. **Один origin.** Клиент раздаёт сам API, поэтому refresh-cookie может быть `SameSite=Strict`, а CORS
   не включается вообще.
2. **Модель сеанса.** Access JWT живёт 5 минут и хранится только в памяти WASM. Refresh-токен — 256 бит
   случайных данных в cookie `__Host-pp_refresh`; в базе хранится только SHA-256. Каждый refresh
   ротирует токен; повторное предъявление уже использованного токена отзывает весь сеанс (token family).
   Каждый запрос с JWT дополнительно проверяет, что сеанс (`sid`) не отозван, — выход и «выйти везде»
   действуют сразу, а не по истечении JWT.
3. **Изоляция данных в три слоя**: (а) сервисы всегда фильтруют по владельцу из проверенного `sub`;
   (б) глобальный именованный фильтр EF Core `owner` для всех `IOwnedEntity` (без аутентифицированного
   пользователя фильтр сравнивает с `Guid.Empty` — fail closed), плюс проверка владельца при сохранении;
   (в) составные внешние ключи `(id, owner_id)` в PostgreSQL, поэтому даже ошибочный код не может
   сослаться на чужой объект.
4. **Деньги.** `decimal` ↔ `numeric(19,4)`, точность проверяется по числу знаков валюты (ISO 4217).
   Баланс не хранится и не принимается от клиента: начальный остаток + сумма проводок (`ledger_entries`).
   Перевод — одна транзакция БД с двумя проводками; перевод между валютами требует явной суммы зачисления
   (курс не угадывается). Суммы по разным валютам никогда не складываются: отчёты группируют по валюте.
   Создание операций идемпотентно (`Idempotency-Key` + уникальный индекс + отпечаток запроса).
   Так как баланс выводится из проводок, параллельные операции не могут «потерять» обновление остатка.
   Advisory-блокировки PostgreSQL (на пользователя и область) применяются там, где нужна схема
   «проверить — затем записать»: проведение повторяющихся операций и режим запрета пересечений в планировщике.
5. **Конкурентные изменения.** Оптимистическая блокировка по системному столбцу `xmin` (`Version` в DTO);
   устаревшая версия → 409 `concurrency_conflict`. Клиент показывает конфликт (например, в
   автосохранении заметок), а не перезаписывает чужие изменения.
6. **Время.** Мгновения — `timestamptz` (UTC), календарные даты — `date`. «Сегодня» вычисляется на сервере
   по IANA-зоне из профиля. Переход DST: несуществующее локальное время сдвигается вперёд, неоднозначное —
   к более раннему мгновению (одно правило на сервере и в клиенте).
7. **Повторения.** Серия задач (правило + шаблон) и материализованные экземпляры; следующий экземпляр
   создаётся при завершении текущего, пропущенные даты не «догоняются»; уникальность
   `(series_id, occurrence_date)` исключает дубли. Повторяющиеся операции проводятся явным идемпотентным
   вызовом `post-due` (уникальность `(recurring_transaction_id, recurrence_date)`), без фоновой задачи,
   действующей от имени всех пользователей.
8. **Email.** Ограниченная очередь (`Channel`) и `BackgroundService`; SMTP (MailKit) в production,
   каталог `.eml` только в Development/Testing. Отправка асинхронна, поэтому время ответа на регистрацию
   и сброс пароля не выдаёт, существует ли адрес.
9. **Идентификаторы.** UUIDv7 генерируются в домене (упорядочены во времени, не раскрывают количество
   записей); EF настроен не генерировать ключи.
10. **Поиск.** Заметки и дневник — сгенерированные столбцы `tsvector` (конфигурация `simple`) + GIN-индексы;
    ввод превращается в безопасный префиксный запрос из букв и цифр. Задачи и операции — поиск подстроки без
    учёта регистра (параметризованный) в пределах данных владельца.

## Клиент

- `AuthSession` хранит access-токен в памяти; обновление идёт через `js/session.js` с `navigator.locks`,
  чтобы вкладки не ротировали один refresh-токен одновременно (иначе сработала бы защита от повторного
  использования).
- `BearerHandler` добавляет токен и один раз повторяет запрос после обновления сеанса при 401.
- Текст интерфейса — встроенные пары `L["русский", "English"]`; форматирование дат, денег и времени — по
  профилю пользователя.
- Никакого `MarkupString`, `innerHTML`, inline-стилей и inline-скриптов: CSP запрещает их, а архитектурные
  тесты не дают их добавить. Позиционирование блоков планировщика — через сгенерированные CSS-классы.
- Клиент — недоверенная среда: все правила и расчёты повторяются на сервере.

## Наблюдаемость

- Структурированные логи (JSON в production): одна строка на запрос (метод, шаблон маршрута, статус,
  длительность) без query string, заголовков, cookie и тела.
- `X-Correlation-Id` формируется сервером (trace id запроса; значение от клиента не принимается), попадает в
  scope всех логов запроса и возвращается в ответе — по нему пользователь может сообщить об ошибке.
- События безопасности с префиксом `security.`: неудачный вход, блокировка после попыток, повторное
  использование refresh-токена (с отзывом сеанса), срабатывание rate limiting (путь без query string),
  удаление аккаунта, выдача роли администратора при старте — с идентификаторами, без паролей, токенов и email.
- `/health/live` (процесс жив) и `/health/ready` (есть соединение с БД); прокси не пропускает `/health/` наружу.
