# Безопасность

Документ описывает реализованные меры защиты, где они находятся в коде и какими тестами подтверждены.
Он не утверждает, что приложение защищено от всех атак: ограничения и непроверенные области перечислены
в конце. Модель угроз — в [THREAT_MODEL.md](THREAT_MODEL.md).

Сообщить об уязвимости: напишите владельцу репозитория приватно (не через публичный issue).

## 1. Аутентификация

| Мера | Реализация | Проверка |
|---|---|---|
| Хеширование паролей | ASP.NET Core Identity (PBKDF2, `PasswordHasher`) | `AuthFlowTests` |
| Политика паролей | длина 12–128, не менее 4 разных символов; без требований к составу (длинные фразы удобнее и надёжнее) | `ValidatorTests`, `AuthFlowTests.Weak_password_*` |
| Подтверждение email | обязательно до входа (`RequireConfirmedEmail`); токены Identity живут 3 часа; ссылка несёт токен во фрагменте URL (`#userId=…&token=…`), поэтому он не уходит на сервер в запросе страницы и в `Referer`, а клиент сразу убирает его из адресной строки | `AuthFlowTests`, E2E `Sign_up_confirm_*` |
| Нейтральные ответы | регистрация, повторная отправка письма и «забыли пароль» всегда отвечают одинаково; для существующего адреса владельцу уходит уведомление; неверный email и неверный пароль дают одну и ту же ошибку; для неизвестного адреса пароль сверяется с фиктивным хешем, чтобы время ответа не отличалось; «email не подтверждён» сообщается только при верном пароле | `AuthFlowTests.Registering_an_existing_email_*`, `Login_failures_are_neutral_*` |
| Блокировка | 8 неудачных попыток → блокировка на 15 минут (Identity lockout), в том числе для верного пароля | `AuthFlowTests.Account_is_locked_*` |
| Access-токен | JWT HS256, 5 минут, claims `sub`, `sid`, `jti`, `role`; проверяются подпись, `iss`, `aud`, срок, список разрешённых алгоритмов (только HS256, `none` отклоняется), `MapInboundClaims=false` | `AuthenticationSecurityTests` (подделка, чужой ключ, изменённое тело, другой алгоритм, `alg:none`, просроченный токен, неверные `iss`/`aud`) |
| Хранение access-токена | только в памяти WASM-приложения; ни `localStorage`, ни `sessionStorage`, ни cookie | E2E (проверка хранилищ и `document.cookie`), архитектурный тест на отсутствие web storage |
| Refresh-токен | 256 бит из CSPRNG, cookie `__Host-pp_refresh` (`HttpOnly; Secure; SameSite=Strict; Path=/`), в БД — только SHA-256; скользящий срок 14 дней, абсолютный срок сеанса 30 дней | `Refresh_cookie_has_host_prefix_*`, `TokenAndKeyTests` |
| Ротация и повторное использование | каждый refresh атомарно «забирает» токен (`UPDATE … WHERE consumed_at IS NULL`) и выдаёт новый; предъявление уже использованного токена отзывает весь сеанс (token family) | `Replayed_refresh_token_revokes_the_family`, `Concurrent_refreshes_*`, `AuthFlowTests.Reusing_*` |
| Немедленный отзыв | каждый запрос с JWT проверяет, что сеанс `sid` активен (`SessionValidator`); выход, «выйти везде», смена и сброс пароля, удаление аккаунта действуют сразу | `Revoked_session_*`, `Logout_*`, `AuthFlowTests.*sessions*` |
| Сеансы | список устройств (user agent, IP, время), отзыв одного или всех; не более 10 активных сеансов (при превышении закрывается давно не использованный); устаревшие записи удаляются через 30 дней | `AuthFlowTests` |
| Ротация ключей подписи | `Jwt:SigningKeys` — набор ключей (минимум 256 бит), подписывает `Jwt:ActiveKeyId`, проверяют все; порядок ротации — в [DEPLOYMENT.md](DEPLOYMENT.md) | `TokenAndKeyTests` |

**Несколько вкладок.** Вкладки одного браузера делят refresh-cookie. Чтобы две вкладки не предъявили один
и тот же токен одновременно (это выглядело бы как кража и отозвало бы сеанс), клиент сериализует refresh
через Web Locks API (`navigator.locks`, `wwwroot/js/session.js`). В браузерах без Web Locks одновременное
обновление в двух вкладках может завершить сеанс — пользователь просто войдёт заново; безопасность при
этом не снижается. Это осознанный выбор строгой политики повторного использования вместо «окна
снисхождения».

## 2. Авторизация и изоляция данных

- **Deny by default**: `FallbackPolicy = RequireAuthenticatedUser`; анонимно доступны только 8 действий
  `AuthController`, справочник `GET /api/v1/profile/reference-data`, health-проверки и статические файлы
  клиента. Список зафиксирован архитектурным тестом `Only_the_allow_listed_actions_are_anonymous` и
  проверен вызовом всех (>60) эндпоинтов без токена (`Every_api_endpoint_except_the_public_auth_ones_requires_authentication`).
- **Владелец только из токена**: `ICurrentUser.UserId` берётся из проверенного `sub`. Ни один контракт
  запроса не содержит `OwnerId`/`UserId` (кроме ссылок из писем, связанных с одноразовым токеном) —
  проверено архитектурным тестом и `Owner_is_always_taken_from_the_token_not_from_the_request`.
- **Mass assignment**: запросы — неизменяемые DTO; неизвестные поля JSON отклоняются (`UnmappedMemberHandling.Disallow`);
  у сущностей нет публичных сеттеров (архитектурный тест); баланс, потраченные суммы, версии и даты
  завершения не принимаются от клиента.
- **IDOR/BOLA**: три слоя (см. [ARCHITECTURE.md](ARCHITECTURE.md#ключевые-решения)): фильтр по владельцу в
  сервисах, глобальный фильтр EF Core (fail-closed), составные внешние ключи `(id, owner_id)` в PostgreSQL.
  Чужой объект неотличим от несуществующего (404). Тесты `DataIsolationTests` проверяют чтение, изменение,
  удаление, списки, поиск, отчёты, экспорт и ссылки на чужие объекты во всех модулях, а также то, что
  база отклоняет межпользовательскую ссылку, даже если обойти проверки приложения.
- **Роли**: роль `admin` (только агрегированная статистика без персональных данных) выдаётся при старте
  адресам из `Bootstrap:AdminEmails`; обычный пользователь получает 403 (`Admin_endpoints_*`).

**Row-Level Security PostgreSQL рассмотрена и не включена.** Причины: приложение использует пул соединений
одной роли, и RLS потребовала бы устанавливать `app.current_user` на каждую транзакцию (риск утечки
контекста между запросами при ошибке в этой логике), усложнила бы миграции и фоновые службы, а гарантия
«нельзя сослаться на чужой объект» уже обеспечена составными FK. Изоляция чтения обеспечивается двумя
независимыми слоями в приложении и покрыта тестами. Если появится прямой доступ к БД для других
приложений или аналитики, RLS стоит включить для этих ролей.

## 3. Защита браузера

| Мера | Значение |
|---|---|
| CSP страницы | `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; manifest-src 'self'; worker-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`. `wasm-unsafe-eval` нужен для компиляции WebAssembly; `unsafe-inline` и `unsafe-eval` не используются. Если в `index.html` появится inline-скрипт, его SHA-256 автоматически добавится в политику, но архитектурный тест запрещает такие скрипты |
| CSP ответов API | `default-src 'none'; frame-ancestors 'none'` |
| Прочие заголовки | `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Permissions-Policy` (камера, микрофон, геолокация, платежи, USB запрещены), `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, HSTS (`max-age=31536000; includeSubDomains`) при `Security:EnableHsts=true` |
| Кэширование | ответы API — `Cache-Control: no-store`; страница-хост — `no-cache` (ETag) |
| CORS | не включён: браузер не получает `Access-Control-Allow-*` ни для какого origin (`Cors_preflight_*`, `Simple_cross_origin_*`) |
| CSRF | обычные API-запросы используют Bearer-токен (не отправляется автоматически). Эндпоинты с cookie (`refresh`, `logout`) требуют `SameSite=Strict` cookie, заголовок `X-CSRF: 1` (кросс-сайтовый запрос с ним невозможен без preflight, а CORS закрыт) и, если браузер их прислал, `Sec-Fetch-Site: same-origin`/`none` и `Origin` из списка разрешённых (`Cross_site_refresh_and_logout_are_rejected`, `CsrfTests`) |
| XSS | Blazor экранирует вывод; `MarkupString`, `innerHTML`, `eval` запрещены архитектурными тестами; E2E-тесты вводят `<script>` и `<img onerror>` в задачи и заметки и проверяют, что никакой диалог не открылся; JSON кодирует `<`, `>` и `&` |
| Открытые редиректы | `returnUrl` после входа принимается только как путь внутри приложения: запрещены `//host`, обратная косая черта, управляющие символы и пробелы, `:` и `|` в пути (`ReturnUrlTests`, включая property-тест, и E2E `Malicious_return_url_is_ignored_after_login`) |
| Формулы в CSV | ячейки, начинающиеся с `= + - @ Tab CR | %`, экранируются апострофом; все поля в кавычках (CWE-1236; `CsvTests`) |

## 4. Ограничение злоупотреблений и ресурсов

| Мера | Значение по умолчанию |
|---|---|
| Глобальный лимит | 300 запросов/мин на пользователя; 60/мин на IP для анонимных (IPv6 группируется по /64) |
| Аутентификация | 10/мин на IP (регистрация, вход, письма, сброс пароля); refresh/logout — 30/мин |
| Тяжёлые операции | экспорт — 5/мин, отчёты — 60/мин на пользователя |
| Ответ при превышении | 429 с `Retry-After` и `code: rate_limited` |
| IP клиента | `X-Forwarded-For` учитывается только от адресов из `Security:KnownProxies`/`KnownNetworks`; без настройки заголовок игнорируется (`Spoofed_forwarded_for_*`, `Forwarded_for_is_honoured_only_*`). nginx перезаписывает заголовок адресом клиента |
| Тело запроса | 1 МБ (Kestrel и собственный middleware, в т.ч. для chunked-запросов), глубина JSON ≤ 16, заголовки ≤ 32 КБ, минимальная скорость передачи тела |
| Время | таймаут запроса 30 с (503), `statement_timeout` 30 с, `lock_timeout` 10 с, `idle_in_transaction_session_timeout` 60 с для роли приложения |
| Запросы | размер страницы ≤ 100, номер страницы ≤ 10 000, поиск ≤ 100 символов, диапазоны дат ≤ 366 дней (планировщик ≤ 42, экспорт ≤ 3660), массовые операции ≤ 100 объектов, генерация повторений ограничена |
| Конкурентность | оптимистическая блокировка (`xmin`), идемпотентность создания операций, атомарные переводы (`ResourceLimitTests`) |
| Перед приложением | nginx: 30 запросов/с на IP (burst 60), 50 соединений на IP, тело ≤ 1 МБ, таймауты |

Ограничение: счётчики rate limiting хранятся в памяти процесса. При нескольких экземплярах приложения
лимиты действуют на каждый экземпляр отдельно; для горизонтального масштабирования нужен общий
счётчик (например, Redis) или лимиты на балансировщике.

CAPTCHA не реализована: регистрация и сброс пароля ограничены по IP, ответы не раскрывают существование
аккаунта, письма отправляются не чаще одного раза в 60 секунд на адрес. При реальных атаках массовой
регистрации CAPTCHA или proof-of-work стоит добавить.

## 5. Данные и секреты

- **Секреты** не хранятся в репозитории и `appsettings*.json` (архитектурный тест проверяет JSON-файлы и
  отсутствие приватных ключей; gitleaks — историю). В production секреты монтируются файлами
  (`PP_SECRETS_DIR`, `*_FILE`) и не видны в `docker inspect`.
- **Ключи Data Protection** (токены Identity) хранятся в БД и шифруются сертификатом
  (`DataProtection:CertificatePath`), поэтому доступ только к базе не позволяет подделать токены подтверждения
  и сброса. Без сертификата в production ключи хранились бы открыто — `generate-prod-secrets.sh` создаёт его.
- **Логи**: только шаблон маршрута, статус и время; без query string, тел, cookie и заголовков авторизации.
  Тест `Passwords_and_tokens_never_appear_in_logs` перехватывает все логи (включая SQL EF Core) во время
  регистрации, входа, refresh и сброса пароля и ищет в них пароли и токены. Архитектурный тест запрещает
  плейсхолдеры `{Password}`, `{Token}` и т.п. в шаблонах логов.
- **Ошибки**: ProblemDetails с машинным `code`; исключения не раскрывают сообщения, стек и имена типов
  (`ErrorMappingTests`, `AllowInputFormatterExceptionMessages=false`).
- **База данных**: приложение работает от роли `pp_app` только с DML-правами на схему `app` (создать или
  изменить таблицу не может — проверено на production-стенде); миграции — от `pp_owner` отдельной задачей.
  PostgreSQL недоступен извне Docker-сети.
- **Удаление аккаунта** требует пароль и слово `DELETE`; все данные пользователя удаляются каскадно в одной
  операции (`Deleting_the_account_requires_password_and_removes_all_user_data`). Резервные копии
  содержат данные до истечения срока их хранения — это нужно учитывать в политике хранения копий.
- **Email-заголовки**: адрес получателя разбирается MimeKit (CR/LF и несколько адресов отклоняются), тема
  кодируется, тело — только text/plain (`EmailMimeTests`).

## 6. Цепочка поставки и контейнеры

- Центральное управление версиями NuGet, `NuGetAudit` (все уровни) и предупреждения как ошибки;
  `dotnet list package --vulnerable --include-transitive` в CI; Dependabot для NuGet, Docker и Actions.
- Базовые образы закреплены по digest; финальный образ без SDK, пользователь `1654` (не root), файлы
  приложения принадлежат root и только читаются, в compose — `read_only`, `cap_drop: ALL`,
  `no-new-privileges`, лимиты памяти и процессов.
- CI: gitleaks (вся история), CodeQL (`security-extended`), hadolint, Trivy (образы и конфигурация),
  SBOM (CycloneDX, syft), OWASP ZAP baseline на развёрнутом стенде (предупреждения роняют сборку,
  исключения обоснованы в `deploy/zap/rules.tsv`).

## 7. Известные ограничения и что не проверено

- Не проводился внешний pentest и ручной аудит кода третьей стороной.
- CI на GitHub выполнен частично (тесты, CodeQL, зависимости, gitleaks — успешно; задача контейнеров ещё не
  выполнялась), алерты CodeQL не просматривались; локально выполнены все тестовые наборы, gitleaks, hadolint,
  Trivy, ZAP baseline — см. [TESTING.md](TESTING.md).
- ZAP baseline — пассивное сканирование; SPA даёт поисковому роботу мало URL. Активное сканирование API
  с аутентификацией не выполнялось.
- Rate limiting — в памяти процесса (см. выше); CAPTCHA нет.
- Соединение приложения с PostgreSQL внутри Docker-сети не шифруется TLS. Если база вынесена на другой
  хост, включите TLS на сервере и `SSL Mode=VerifyFull` в строке подключения.
- 2FA/WebAuthn не реализованы.
- Клиентская часть Blazor не измеряется инструментом покрытия (.NET coverage не видит код в браузере);
  она проверена E2E-тестами.
